# Stage 3 — Agent Benchmark, Independent Oracles, and Fault Matrix

## Dataset

- Dataset version: `1.0.0`.
- 30 samples, each with a stable `sample_id`, visible fixture, and hidden oracle files.
- Fixture digest binds the prompt, visible files, hidden oracle files, worker graph, allowed paths,
  forbidden paths, required artifacts, and tool contract.

| Category | Count | Implementation |
|---|---:|---|
| Bug fix + regression | 10 | Small Python repositories with a seeded behavior bug and a hidden pytest oracle |
| Multi-file feature | 5 | Package/module implementations with hidden contract tests |
| Tool discovery / MCP | 5 | Real stdio MCP server under M1 `tool.search` / `dispatch_action` |
| Multi-worker collaboration | 5 | 2–3 worker AnyCode DAGs with dependency-ordered artifact handoff |
| Long context | 5 | 14–18 archived distractor documents plus one authoritative long specification |
| Recovery / safety | separate 19-case matrix | Real OpenSandbox OS-process Stage D evidence plus deterministic fault injection |

The five-task category is **long-context**, not five LLM-driven recovery tasks. AtlasOS has a
trusted Stage D recovery path, but normal coding sessions do not expose an agent-level suspension
API that would make an LLM recovery task honest. Recovery is therefore evaluated through the
fault-injection matrix rather than by inventing a runtime feature for the benchmark.

## Independent acceptance

Every coding sample is checked by a Host-only oracle after sandbox export:

1. hidden pytest suite never present in the sandbox;
2. visible regression tests still pass;
3. only allowed paths changed;
4. forbidden paths (especially `tests/`) unchanged;
5. required artifacts exist;
6. Host fixture digest unchanged;
7. multi-worker oracle verifies distinct workers, non-empty worker outputs, and artifact delivery;
8. tool oracle verifies `tool.search` occurred, the exact MCP tool(s) were dispatched, and the tool
   output contract was met.

The tool tasks use the real deterministic stdio MCP server
`experiments/evaluation/mcp_servers/evaltools.py` through AtlasOS M1. The server is read-only.

All hidden suites were checked against the untouched visible fixture: every hidden suite fails or
errors on the baseline fixture, so the oracle is discriminating rather than trivially passing.
Multi-worker hidden suites fail at import on the empty baseline; coding/long-context suites fail on
the seeded behavior; tool suites fail because `answer.txt` does not exist.

## Safety and recovery matrix

Generated by:

```powershell
python -m experiments.evaluation.reliability `
  --stage-d experiments/results/stage-d-s1-fix-2.json `
  --output experiments/results/evaluation/reliability_matrix.json
```

Result: **19/19 expected safe outcomes**, 11 real OpenSandbox OS-process cases and 8 deterministic
fault-injection cases.

A correct refusal is scored as a safety success. The matrix is separate from capability task
success and is not reported as a model-quality win.

## What the benchmark intentionally does not do

- It does not use FakeSandboxProvider for capability runs. Fake providers appear only in the
  deterministic unit/integration tests that do not claim real isolation.
- It does not infer success from the agent's final message.
- It does not share sandboxes, worker state, SQLite stores, or trajectory runs between samples.
- It does not weaken M3/M4/M5/M6 to improve scores.
- It does not claim tool-discovery tasks in the AnyCode baseline: AnyCode 0.9.0 has no equivalent
  of the AtlasOS M1 progressive MCP surface, so those tasks are reported `NOT_EVALUATED` for the
  baseline instead of being silently compared.

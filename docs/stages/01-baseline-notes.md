# Stage 1 Baseline Notes

Frozen baseline for AtlasOS V1. Recorded 2026-10-22 on Windows, Python 3.12.15, AnyCode 0.9.0.

## What Stage 1 proves

A three-task static workflow runs through the upstream AnyCode engine, every inference call is
recorded with provider-reported cache tokens, task outcomes are normalized from upstream task
state, and the whole run is persisted as one JSONL record. No AtlasOS selection, rendering,
compaction, or scheduling logic exists yet.

## Runtime shape

`AtlasRuntime` only composes upstream pieces:

1. validate that the configuration is honest for Stage 1 (baseline scheduler/context labels,
   ContextPilot off),
2. register one AnyCode provider per agent, with a usage callback that attributes records,
3. compile Atlas tasks to AnyCode `TaskSpec`, create a team, and call `AnyCode.run_tasks` once,
4. read task outcomes from the run's upstream checkpoint and normalize them,
5. aggregate metrics, estimate cost when pricing is configured, append one JSONL record.

It owns no queue, executor, wave builder, or scheduler.

### Why task results come from the checkpoint

`TeamRunResult.agent_results` is keyed by agent name, so when one agent executes several tasks
only the last result survives. `Team.get_tasks()` is also empty after `run_tasks`: the upstream
engine keeps its queue local to the call. The only upstream-maintained task state for a run is
the checkpoint (`CheckpointConfig`), which persists `Task` records with status and result after
each wave. Each Atlas run therefore owns a checkpoint directory and reads the newest file from
it, avoiding any dependence on private workflow-id derivation.

## Task identity

`AtlasTaskSpec.task_id` is stable and kebab-case; `title` is display text. The compiler:

- rejects duplicate titles (AnyCode resolves dependencies by title),
- resolves `depends_on` task ids to titles at the boundary,
- attaches the run input only to root tasks,
- rejects unknown agents/dependencies, cycles, and multiple final tasks,
- rejects two tasks of the same agent in one dependency wave, because attribution and agent
  reuse assume sequential per-agent execution.

## Baseline workload and prompt layout

`baseline_workflow()`: root input -> Research A (researcher-a), Research B (researcher-b) ->
Review (reviewer). There is no LLM planner.

The prompt is upstream-rendered: `system_prompt`, then the task prompt built by
`AnyCode._build_task_prompt` (task title, description, and prerequisite results truncated to
`DEPENDENCY_CONTEXT_MAX_LENGTH`). This is the frozen `context_policy = "upstream_default"`; it is
**not** full history.

Each agent's system prompt is a shared `STABLE_SYSTEM_PREFIX` (no ids, timestamps, metrics, or
per-turn state) followed by a `Role:` line, approximating the architecture's "stable system
prefix, then stable agent role" layout without adding a renderer. Agents run with `tools=[]`;
otherwise AnyCode exposes built-in shell tools and the model tries to explore the filesystem,
which fails on Windows and marks tasks failed.

Frozen labels:

```text
scheduler_policy     = "upstream_default"
context_policy       = "upstream_default"
contextpilot_enabled = false
```

## Metrics and fingerprints

The DeepSeek adapter measures tokens, cache split, latency, and prompt fingerprints; the runtime
attributes each observation to run/task/agent using task-start/task-complete progress events and
one provider per agent. Missing provider cache fields stay `None`; aggregation is token-weighted.

Fingerprints are SHA-256 over a canonical JSON payload:

- `stable_prefix_hash` = system prompt + tool definitions,
- `full_prompt_hash` = the above + rendered messages.

They are metadata only and are never injected into prompts.

## Known limitations

- Task timing is derived from `Task.created_at`/`updated_at`, so it includes queue wait and has
  timestamp resolution only; there is no upstream per-task start/end event.
- One agent may execute several tasks, but not two tasks in the same wave; the compiler rejects
  that shape.
- Agent adapters are cached by AnyCode per agent, so a fake adapter's scripted responses are
  consumed across that agent's tasks in order.
- Every run registers new provider names in AnyCode's process-global registry; long-lived
  processes accumulate registrations.
- Cache behavior is best-effort and depends on provider-side block granularity and eviction.
